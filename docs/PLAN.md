## 1. الرؤية والهدف

### 1.1 المشكلة التي نحلها
البرنامج المرجعي (MHDesign) عبارة عن **إضافة (Plugin) داخل SketchUp** — يعني المستخدم لازم:
- يشتري SketchUp ويتعلم استخدامه.
- يثبّت الإضافة على جهازه.
- يشتغل على جهاز واحد فقط.
- ما يقدر يشارك التصاميم مع فريقه بسهولة.
- التحديثات بطيئة وتعتمد على تحديث الإضافة محلياً.

### 1.2 الحل
**برنامج سحابي (SaaS) كامل يعمل من المتصفح**، بدون الحاجة لـ SketchUp ولا تثبيت، بمميزات:
- تصميم مطابخ ثلاثي الأبعاد من المتصفح مباشرة.
- مكتبة قوالب جاهزة (وحدات سفلية، علوية، أركان، دواليب، إكسسوارات).
- كل قالب **مرن** يقبل تعديل الأبعاد والخامات قبل دمجه في المطبخ.
- إصدار فواتير وعروض أسعار للعملاء.
- مخطط القص (Cutting Diagram) لتحويل التصميم إلى تصنيع فعلي.
- يدعم **3 لغات:** العربية، الإنجليزية، الصينية.
- متعدد المستخدمين (Multi-tenant) — كل شركة عندها حسابها وعملاءها وتصاميمها.

### 1.3 الجمهور المستهدف
- **محلات ومصانع المطابخ** (سعودي، مصري، خليجي، صيني).
- **المصممين الداخليين** اللي يقدمون خدمة تصميم مطابخ.
- **النجارين والورش** اللي يحتاجون مخطط قص دقيق.

## 3. المعمارية التقنية (Tech Stack) — مخصصة للمبتدئ

> **ملاحظة:** اختياراتنا التقنية مبنية على: (1) سهولة التعلم، (2) مجتمع كبير وموارد عربية/إنجليزية، (3) قدرتها على تنفيذ المتطلبات.

## 4. مراحل التطوير (Roadmap)

> **استراتيجية MVP:** نبني نسخة بسيطة جداً تعمل أولاً، ثم نضيف المميزات تدريجياً. هذا أسلوب صحي للمبتدئ — يخليك تشوف نتيجة بسرعة وتتعلم من كل خطوة.

### المرحلة 0: التعلم والتأسيس (4-8 أسابيع)
**الهدف:** اكتساب المهارات الأساسية قبل بدء البناء.

- [ ] تعلم أساسيات HTML/CSS/JavaScript (إذا لم تكن متمكناً).
- [ ] تعلم React الأساسية من خلال دورة (مثل [react.dev](https://react.dev) أو دورة عربية).
- [ ] بناء مشروع بسيط بـ Next.js (مثلاً: To-Do List).
- [ ] فهم أساسيات قواعد البيانات (SQL أساسي + Prisma).
- [ ] فهم أساسيات Three.js (تجربة عرض مكعب 3D وتدويره).
- [ ] إعداد بيئة العمل: VS Code, Node.js, Git, GitHub.

**مخرجات هذه المرحلة:** مشروع تجريبي صغير على GitHub + قدرة على متابعة البناء.

#### 1.1 البنية الأساسية

#### 1.3 مكتبة القوالب (بدون 3D — جداول فقط)

## 5. نموذج البيانات (Database Schema — مبسط)

```
User (المستخدم)
  ├─ id, email, name, language
  └─ ينتمي إلى → Workspace

Workspace (الشركة / مساحة العمل)
  ├─ id, name, plan (free/pro/enterprise)
  └─ يملك: Customers, Projects, Templates, Materials

Customer (العميل)
  ├─ id, name, phone, address, notes
  └─ ينتمي إلى → Workspace

Project (المشروع / المطبخ)
  ├─ id, name, customer_id, status
  ├─ design_data (JSON — يحتوي مواقع وأبعاد الوحدات)
  └─ ينتمي إلى → Workspace

Template (القالب الجاهز)
  ├─ id, name, category (lower/upper/corner/...)
  ├─ default_dimensions, configurable_options (JSON)
  └─ scope: global أو workspace-specific

Material (الخامة)
  ├─ id, name, type (HPL/MDF/...), price_per_m2, thickness
  └─ ينتمي إلى → Workspace

Invoice (الفاتورة)
  ├─ id, project_id, total, status (draft/sent/paid)
  └─ line_items (JSON)
```

## 6. التحديات الكبيرة وكيف نتعامل معها

### التحدي #1: محرر 3D
- **الصعوبة:** عالية جداً للمبتدئ.
- **الحل:** استخدام React Three Fiber (أسهل من Three.js الخام) + الاعتماد على القوالب البرمجية procedural بدل ما نتعامل مع نماذج GLB معقدة.
- **مصدر تعلم:** [r3f.docs.pmnd.rs](https://r3f.docs.pmnd.rs/)

### التحدي #2: خوارزمية مخطط القص
- **الصعوبة:** متوسطة.
- **الحل:** استخدام مكتبة جاهزة مثل `guillotine-packer` بدل تنفيذها من الصفر.

### التحدي #3: دعم اللغة الصينية والـ RTL/LTR
- **الصعوبة:** متوسطة.
- **الحل:** next-intl يتكفل بمعظم العمل. الترجمة الفعلية للنص الصيني تحتاج مترجم محترف.

### التحدي #4: الأداء — التصاميم الكبيرة بطيئة
- **الصعوبة:** ستظهر متأخراً.
- **الحل:** نتركها للمرحلة 5 (تحسينات). الآن نركز على الوظائف.

### التحدي #5: الحجم الكامل للمشروع
- **الصعوبة:** المشروع كبير جداً لشخص واحد مبتدئ.
- **التوصية:**
  1. **التزم بالـ MVP أولاً** ولا تحاول تنفذ كل شيء.
  2. اعرض MVP على ورشة صديقة كـ"تجربة" قبل ما تطور المراحل التالية.
  3. فكر في شريك تقني بعد المرحلة 2.
  4. توقع المشروع كاملاً يحتاج **12-18 شهر** بدوام كامل، أو **24-36 شهر** بدوام جزئي.

## 11. نظام MCP (Model Context Protocol) — الميزة التنافسية الكبرى

### 11.1 ما هو MCP ولماذا نضيفه؟

**MCP (Model Context Protocol)** بروتوكول مفتوح من Anthropic يخلي نماذج الـ AI (مثل Claude، ChatGPT، Cursor، إلخ) تتفاعل مع التطبيقات الخارجية بشكل موحد. باختصار: **يحوّل برنامجنا إلى أداة قابلة للأتمتة بالكامل عبر AI**.

**لماذا هذي ميزة قاتلة لمنتجنا:**
1. **تجربة مستخدم ثورية:** المصمم يكتب "صمم مطبخ ركن 4×3 متر مودرن أبيض مع جزيرة في النص" والـ AI يبنيها فعلياً في البرنامج.
2. **التكامل مع أدوات السوق:** أي مستخدم عنده Claude Desktop أو Cursor يقدر يربط برنامجنا ويصمم منه مباشرة.
3. **API ثاني مجاناً:** الـ MCP server هو فعلياً واجهة API كاملة — نستخدمها داخلياً وخارجياً.
4. **ميزة لا توجد في MHDesign ولا أي منافس عربي.**

### 11.2 المعمارية — نوعان من التكامل

```
┌─────────────────────────────────────────────────────────────┐
│  (1) مساعد AI داخلي                                          │
│  المستخدم يكتب في المحرر: "أضف خزانة 80 سم تحت الشباك"      │
│  ↓                                                            │
│  AI (Claude API) → يستدعي MCP Tools داخلياً → ينفذ التغيير  │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│  (2) MCP Server عام (Remote)                                 │
│  مستخدم Claude Desktop يربط حسابه عندنا → يصمم من Claude    │
│  AI خارجي (Claude, ChatGPT, Cursor) → MCP Server → برنامجنا │
└─────────────────────────────────────────────────────────────┘
```

### 11.4 التقنيات والمعيار (محدّث وفق MCP Spec 2026)

| البند | الاختيار | التفاصيل |
|------|----------|---------|
| **SDK** | `@modelcontextprotocol/sdk` (TypeScript — Tier 1) | يدعم Zod schema validation تلقائياً |
| **Transport** | **Streamable HTTP** (المعيار الحالي 2026) | HTTP POST + SSE اختياري — STDIO للاختبار المحلي فقط |
| **Auth** | **OAuth 2.1** متوافق مع MCP spec | كل request يحمل `Authorization: Bearer <token>` |
| **عزل المستأجرين (Tenants)** | RFC 8707 `resource` parameter | الـ token مربوط بـ MCP server محدد — يمنع سرقة tokens بين الـ workspaces |
| **Server Location** | Next.js API Route: `/api/mcp` | باستخدام `StreamableHTTPServerTransport` |
| **Scopes** | `designs:read`, `designs:write`, `invoices:create`, إلخ | كل token يحدد ما يستطيع فعله |
| **Client ID** | Client ID Metadata Document (URL-based) | `https://skdc.app/oauth/metadata.json` |

**ملاحظات تنفيذية مهمة:**
- لا تستخدم `console.log()` في STDIO transport (يفسد المخرجات) — آمن في HTTP.
- استخدم Zod schemas لكل Tool input — تتحقق تلقائياً.
- الـ server يتحقق أن الـ token صادر له هو تحديداً (audience binding) — يمنع هجمات cross-tenant.

### 11.6 نقاط مهمة للتنفيذ

1. **ابدأ بالداخلي قبل الخارجي:** أبني MCP layer داخلي يستخدمه المساعد المدمج أولاً، ثم لاحقاً أعرضه كـ Remote MCP Server.
2. **كل Tool يجب أن يكون آمناً ومحدوداً:** مثلاً `remove_unit` لا يحذف بدون تأكيد المستخدم.
3. **Rate limiting من البداية:** الـ AI ممكن يستدعي مئات الـ Tools في ثوان — نحدد سقف.
4. **Audit log:** سجل كل استدعاء MCP (من، متى، أي Tool) — مهم للأمان وتصحيح الأخطاء.
5. **اختبر مع Claude Desktop أولاً:** أسهل بيئة اختبار قبل الإطلاق العام.

## 12. ميزة Image-to-Design — تحويل الصورة إلى تصميم بالذكاء الاصطناعي

### 12.1 الفكرة

المستخدم يرفع **صورة** (تصوير لمطبخ موجود، رسم يدوي، صورة Pinterest، مرجع كتالوج)، والذكاء الاصطناعي يحلل الصورة ويولّد **تصميم 3D قابل للتعديل** يطابق الصورة الأصلية بنسبة ~95%، يبقى للمستخدم تعديل الـ 5% المتبقية يدوياً.

> **هدف الجودة:** 95% — لكن واقعياً نبدأ بـ 70-80% في الإصدار الأول ونتحسن مع كل تكرار وبيانات تدريب أكثر.

### 12.2 أنواع الصور المدعومة

| النوع | المثال | الصعوبة |
|------|--------|--------|
| **صورة مطبخ موجود** | المالك يصور مطبخه الحالي ويبغى نسخة محسّنة | متوسطة |
| **صورة مرجعية** | صورة من Pinterest أو كتالوج | عالية (الأبعاد غير معروفة) |
| **رسم يدوي / Sketch** | المصمم يرسم سريعاً ويصورها | عالية جداً |
| **مخطط معماري 2D** | Plan view للغرفة | منخفضة (واضح ودقيق) |
| **Floor Plan + صور جانبية** | الأمثل: مخطط + صور للجدران | منخفضة + دقيقة |

### 12.3 كيف يعمل؟ (Pipeline تقني)

```text
1. المستخدم يرفع الصورة
       ↓
2. المستخدم يدخل بيانات أساسية مساعدة:
   - أبعاد الغرفة (طول × عرض × ارتفاع) ← مهم جداً للأبعاد الدقيقة
   - عدد الجدران + مواقع النوافذ والأبواب
       ↓
3. AI Vision Model (Claude Opus 4.7 Vision / GPT-4 Vision):
   - يكتشف الوحدات (سفلية، علوية، أركان، أجهزة)
   - يقدّر مواقعها وأبعادها النسبية
   - يحدد الخامات والألوان
   - يخرج JSON منظم
       ↓
4. مطابقة الوحدات مع مكتبة القوالب:
   - "وحدة سفلية درجين" → matches `lower-2-drawer` template
   - استخدام Embeddings للمطابقة الذكية
       ↓
5. توليد تصميم 3D من JSON:
   - استخدام نفس engine الـ 3D editor
   - وضع كل وحدة في موقعها
       ↓
6. عرض النتيجة للمستخدم في المحرر للتعديل
       ↓
7. حفظ كمشروع عادي قابل لإصدار فاتورة ومخطط قص
```

### 12.4 التقنيات المختارة

| الطبقة | التقنية | الاستخدام |
|--------|---------|----------|
| **Vision Model** | Claude Opus 4.7 (multimodal) أو GPT-4o | تحليل الصورة وإخراج JSON منظم |
| **Structured Output** | Anthropic structured outputs / OpenAI JSON mode | ضمان JSON صحيح من الـ AI |
| **Embeddings** | OpenAI text-embedding-3 / Voyage AI | مطابقة الوحدات مع القوالب |
| **Vector DB** | pgvector (داخل PostgreSQL) | تخزين embeddings للقوالب |
| **Depth estimation** | MiDaS أو Depth Anything v2 | تقدير العمق من صورة 2D (اختياري) |
| **Image storage** | Cloudflare R2 + Image Resizing | تخزين ومعالجة الصور المرفوعة |

### 12.5 التحديات والقيود

| التحدي | الحل |
|--------|------|
| **الأبعاد غير دقيقة من الصورة وحدها** | نطلب من المستخدم إدخال أبعاد الغرفة كحد أدنى |
| **العمق صعب تقديره من 2D** | نقترح على المستخدم رفع 2-3 زوايا للغرفة |
| **زاوية التصوير تشوّه النسب** | نستخدم perspective correction قبل التحليل |
| **خامات قد لا تطابق المكتبة** | نعرض أقرب 3 بدائل ونخلي المستخدم يختار |
| **التكلفة (كل تحليل = $0.05-0.20)** | نخلي الميزة محسوبة بـ credits أو limited بالخطة |
| **الدقة الواقعية أقل من 95%** | نُسوّق "تصميم مبدئي تعدّله بثوان" بدل "دقة 100%" |

### 12.6 سيناريوهات استخدام

**سيناريو 1: العميل المتردد**
> عميل لديه صورة من Instagram يحبها. يرفعها، يدخل أبعاد مطبخه، خلال 30 ثانية يشوف نسخة 3D قابلة للتعديل من المطبخ الذي يحلم به. الورشة تبيعه بنصف الوقت.

**سيناريو 2: تحديث مطبخ موجود**
> مالك بيت قديم يصور مطبخه ويرفعه. الـ AI يحلل ويعرض النسخة الحالية في 3D، ثم يقترح ترقيات (تبديل خامة، إضافة وحدات، تحسين التوزيع).

**سيناريو 3: المصمم السريع**
> مصمم محترف يرسم بسرعة بقلم على ورقة، يصور الرسمة، يحصل على تصميم 3D كامل في دقيقة بدل ساعة عمل يدوي.
